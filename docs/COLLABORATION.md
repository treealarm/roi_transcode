# Совместная работа над ТЗ и планом

Над `smart-video-encoder` работают двое, каждый со своим агентом (Claude Code и Cursor).
ТЗ заказчика ещё правится. Ниже — как не затереть друг друга.

## Что здесь общее

| Файл | Кто владеет | Как меняется |
|---|---|---|
| `smart-video-encoder_TZ_v2.0.pdf` | заказчик | только заменой файла целиком, с новой версией в имени |
| `plan-v2.md` | оба, по очереди | правки через git, по правилам ниже |
| `STATUS.md` | оба | короткий handoff по фактическому состоянию кода |
| `COLLABORATION.md` | оба | редко |

Обсуждения в чатах агентов **не являются** общим состоянием: второй агент их не видит.
Всё, что должно пережить смену смены, попадает в эти файлы и коммитится.

## Быстрый вход для следующего агента

Перед началом работы открыть:

1. [`STATUS.md`](STATUS.md) — что уже сделано в коде и что делать дальше.
2. [`plan-v3-library.md`](plan-v3-library.md) — детали по library track.
3. [`plan-v2.md`](plan-v2.md) — общий план и открытые вопросы к заказчику.

## Очередь

Владение планом обозначено строкой ниже. Меняет её тот, кто **берёт** работу, и тот,
кто **отдаёт**, — отдельными коммитами.

<!-- BATON -->
**Ведёт:** Данил (Claude Code)
**С:** 2026-08-26
**Над чем:** сверка плана с v3 — раздел «Что изменила v3» записан, перенумерация ссылок
и решения по расхождениям (модель важности, §13, VBR) ещё не сделаны
<!-- /BATON -->

Порядок:

1. `git pull` — всегда, до чтения плана, а не только до правки. План мог измениться.
2. Проставить себя в блоке выше, закоммитить **одной** правкой, запушить. Это и есть
   взятие очереди.
3. Работать. Правки плана коммитить по ходу, не копить.
4. Освобождая — вернуть `свободно` и запушить.

Если строка занята, а человек недоступен — не отбирать молча. Написать второму и
дождаться; конфликт в плане дороже ожидания.

## Правила правок плана

**Не переписывать разделы целиком.** Если раздел кажется неверным — добавить рядом
пометку с датой и инициалами, а не заменять. Так виден спор, а не результат
последнего сохранения.

**Каждое утверждение о состоянии кода — проверенное.** В плане есть таблица «что уже
есть». Строка в ней означает, что человек это открыл и увидел, а не предположил.
Ошибка здесь дороже любой другой: по ней принимают решение не делать работу.

**Решения записывать с причиной.** «Rockchip откладываем» бесполезно через месяц.
«Rockchip откладываем: нет RK3588 и arm64-раннера, заказчик подтвердил 2026-08-22» —
годится.

**Открытые вопросы держать в своём разделе плана,** а не растворять по тексту. Ответы
на них меняют объём работ в разы, и они должны быть видны с одного взгляда.

## Когда ТЗ обновится

1. Новый PDF кладётся рядом, старый **не удаляется** — иначе нечем свериться, что
   изменилось.
2. Тот, кто первым увидел, дописывает в план раздел «Изменения ТЗ vN → vN+1»: что
   добавилось, что отпало, что из уже сделанного стало ненужным.
3. Только после этого правится основная часть плана.

Последний пункт важен: без явного списка изменений через две версии никто не сможет
сказать, почему в плане есть задача, которой в ТЗ больше нет.

## Код

Общие файлы кода — те же правила, что и у всего репозитория: ветка, коммит, пуш.
Очередь из этого документа распространяется **только на план и ТЗ**; код можно писать
параллельно, git разведёт.

Исключение — `proto/roi_transcode.proto`: контракт, который держат обе стороны и
ta_vms. Правки в нём согласовывать, как план.
