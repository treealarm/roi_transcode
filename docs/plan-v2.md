# План работ по ТЗ smart-video-encoder v2.0

Источник: [`smart-video-encoder_TZ_v2.0.pdf`](smart-video-encoder_TZ_v2.0.pdf) в этом каталоге.
Порядок совместной работы над этим файлом — [`COLLABORATION.md`](COLLABORATION.md).

## Как читать этот план

Мы одновременно **исполнитель** ТЗ и **первый потребитель** результата: `roi_transcode`
уже встроен в ta_vms и пережимает архивные клипы. Поэтому у каждой задачи два
вопроса — «требует ТЗ» и «нужно продукту», и они не всегда совпадают. Там, где
расходятся, это отмечено явно.

Плана «с нуля» не существует: значительная часть P0 уже сделана и работает.
Первый раздел — про это, чтобы никто не переделывал заново.

## Чего нет и что решать

### Блок A. Ядро адаптивности — расхождение с ТЗ самое глубокое

ТЗ описывает **модель важности** (§11) и **object-first rate control** (§15). У нас
ни того, ни другого: есть плоская таблица «kind → qp_delta» и постоянный квантователь.

| Требование | Сейчас | Что делать |
|---|---|---|
| `Object{track_id, class_id, confidence, semantic_priority, task_priority, critical}` (§10) | только `kind` + геометрия | расширить публичный тип; **данные уже есть** в архиве ta_vms — `MetadataBox` несёт `track_id` и `confidence` |
| Importance = произведение 5 факторов, I(x,y) ∈ [0,1] (§11) | нет | ввести слой importance между объектами и qp-map; сегодняшняя таблица становится частным случаем `semantic_priority` |
| Polygon (§2) | нет | растеризация в ту же qp-map, что и маска |
| Temporal ROI: `max_missing_frames`, decay, smoothing, prediction (§13) | только `hold_sec` — фиксированное окно вокруг сэмпла | по `track_id`; **важно:** для архива интерполяция не-каузальная (будущее трека известно), для живого потока — предсказание |
| QualityPolicy: OBJECT_FIRST / BALANCED / BITRATE_FIRST (§14) | нет | `Settings`; дефолт по ТЗ — OBJECT_FIRST |
| Object-first rate control с бюджетом битрейта (§15) | нет, только CQP/CRF | **самая крупная работа блока**, см. ниже |

**Про rate control.** Сейчас независимость QP-офсетов по блокам держится ровно на том,
что мы кодируем в CQP. Целевой битрейт (§15) эту независимость ломает: rate control
начнёт перераспределять биты между ROI и фоном. Это не недоработка, а физика, и ТЗ
требует именно второго режима. Значит `FileSettings` и `StreamSettings` разойдутся
здесь — они уже разделены в proto специально под это.

### Блок B. Бэкенды

| Бэкенд | Состояние | Что делать |
|---|---|---|
| Intel oneVPL | работает | добавить runtime capability query вместо сегодняшних допущений |
| Software | работает | — |
| NVENC | объявлен, `qpDeltaMap` **не передаётся в SDK** | доделать; нужна NVIDIA-машина, у нас её нет |
| Rockchip MPP | нет вообще | новый бэкенд, P0 по ТЗ (RK3588/RK3588S); нужно железо |
| `IEncoderBackend` + `EncoderCapabilities` (§6.4, §7) | нет; `RoiEncoder` монолитен | вынести интерфейс, переложить существующие три реализации |

**Важно про порядок:** интерфейс бэкенда и capability discovery надо сделать **до**
Rockchip, а не после. ТЗ прямо предупреждает (§6.4), что число ROI и QP API у разных
SoC разные, и наш нынешний код это допущение зашивает.

### Блок C. Память и zero-copy

ТЗ требует `MemoryType{CPU, AVFRAME, CUDA, VAAPI, ONEVPL, ROCKCHIP_MPP, DMABUF}` (§8).
Сейчас `Session::Frame` принимает CPU-планы или один сжатый access unit. Для ta_vms
этого достаточно; для ТЗ — нет. Работа осмысленна только вместе с блоком B.

### Блок D. SEI-метаданные (§16)

Полностью отсутствует. Три режима: full frame, delta, periodic checkpoint.
**Продукту сегодня не нужно** — детекции и так лежат в БД рядом с клипом. Нужно, когда
поток отдаётся наружу третьей стороне.

### Блок E. Тестирование и метрики

Здесь разрыв количественный, а не качественный: каркас есть, датасетов и метрик нет.

| Уровень ТЗ | Состояние |
|---|---|
| L1 Unit (§18) | есть |
| L2/L3 Component / Software integration | частично (`check.sh`) |
| L4 Hardware integration (§29) | руками; CI нет |
| L5 Quality / RD (§38–41): PSNR, SSIM, MS-SSIM, VMAF, ROI-VMAF, QSI, RD-кривые | PSNR и SSIM по маскам (ROI / фон / глобально) — `tests/quality/roi_metrics.cpp`; RD-кривая в 5 точках — `benchmarks/synthetic/rd_curve.sh`. **VMAF, MS-SSIM, QSI — нет** |
| L6 Task-aware (§42): mAP, HOTA, IDF1, OCR | нет |
| Датасеты: BVI-HD, BDD100K, MOT17, UFPR-ALPR (§20–25) | нет |
| ROI boundary test (§44) | есть: пять концентрических полос вокруг края, дифференциалом к базовому кодированию (`roi_metrics --baseline`), с порогом в `check.sh` |
| Temporal quality instability (§43) | есть: `mean|Q(t) − Q(t−1)|` отдельно по ROI и фону, там же |
| Regression framework (§46) | нет |

**Замечание по существу.** ТЗ само предупреждает (§40), что global VMAF не может быть
единственным KPI, а QSI (§41) не является самостоятельным. Значит осмысленный ответ даёт
только **пара «область / фон»**, и метрика считается по маскам, а не по кадру целиком.

Сделано именно так, но на PSNR и SSIM: они точны, не требуют модели и не тянут
зависимость. VMAF ложится сверху тем же способом — по уже разобранным плоскостям Y.
Обрати внимание: в порту vcpkg `ffmpeg` фичи `vmaf` **нет вовсе**, есть отдельный порт
`libvmaf`. То есть ROI-VMAF всё равно пришлось бы линковать в метрику напрямую —
фильтром ffmpeg он по маске не считается (2026-08-23).

Первое измеренное: адаптивное кодирование даёт **+4.8…+7.6 dB в области** на пяти точках
CRF, и на трёх из пяти при этом файл **меньше** базового (`testdata/eval/rd_moving_cpu_h264.csv`).

### Блок F. CI и структура репозитория

ТЗ требует **GitLab CI** (§30–37) с runner'ами по тегам `nvidia`, `intel-qsv`,
`rockchip-rk3588`, и структуру каталогов (§52). Мы на GitHub, внутри монорепозитория
ta_vms, без hardware-runner'ов.

Это **решение, а не задача**: см. открытые вопросы.

## Открытые вопросы к заказчику

Ответы меняют объём работ в разы, поэтому их стоит закрыть до начала.

1. **Rockchip — реальный target или «на будущее»?** P0 по ТЗ, но требует железа
   (RK3588) и отдельного arm64-раннера. В нашем продукте RK-плат сейчас нет.
2. **GitLab обязателен?** Мы в GitHub-монорепозитории. Варианты: перенести
   `smart-video-encoder` в отдельный GitLab-репозиторий (тогда ta_vms подключает его
   как зависимость), либо согласовать GitHub Actions с теми же стадиями.
3. **Отдельный репозиторий для библиотеки?** ТЗ описывает самостоятельный продукт со
   своей структурой (§52). Против выделения — общий proto с ta_vms; см. запись в
   [плане ROI](../../docs/) о том, во что обошёлся OnvifLib в трёх копиях.
4. **NVENC — есть ли машина** для разработки и CI?
5. **Датасеты:** кто и куда их кладёт. BVI-HD + BDD100K + MOT17 + UFPR-ALPR — это
   сотни гигабайт; ТЗ предлагает fast corpus 5–20 ГБ с checksum-манифестом (§26).
6. **Какой глубины ждут от `IEncoderBackend` (§7)?** У нас все бэкенды идут через
   libavcodec: ROI уезжает в железо как side data `AV_FRAME_DATA_REGIONS_OF_INTEREST`,
   которую ffmpeg переводит в `mfxExtEncoderROI` (QSV), `VAEncMiscParameterBufferROI`
   (VA-API) и `quantOffsets` (x264/x265). Прямых вызовов SDK нет ни одного. По форме §7
   выполняется, по глубине — нет, и цена видна: `mfxExtMBQP` ffmpeg не пробрасывает,
   поэтому per-block QP на Intel недоступен (маска вырождается в прямоугольники), а
   nvenc-обёртка ROI-side-data не читает вовсе. Переход на прямые SDK — это три
   зависимости и три реализации подачи кадров; делать его стоит только по явному
   требованию либо по измерению, что поблочный QP даёт заметно больше прямоугольников
   (2026-08-23).

## Порядок работ

Опирается на порядок из §54 (core → FFmpeg → NVENC → oneVPL → Rockchip → adaptive ROI
→ metrics → benchmark), но переставлен: у нас уже сделаны FFmpeg, oneVPL и software, а
метрики нужны **раньше** новых бэкендов — иначе их не на чем принимать.

### Этап 1. Измеримость (без неё всё остальное на глаз)

1. ~~PSNR и SSIM по маскам, парой «область / фон»~~ — сделано, `roi_metrics`.
2. ~~**RD-кривые** (§38), baseline против adaptive~~ — сделано для H.264/CPU;
   остались H.265 и QSV, скрипт тот же.
3. ~~**Temporal quality instability** (§43)~~ — сделано по ROI и фону; по `critical`
   появится вместе с самим полем (этап 2).
4. ~~**ROI boundary test** (§44) — пять зон вокруг границы~~ — сделано.
   **Поправка от 2026-08-23 к первому прочтению.** Сначала я записала сюда, что рамка на
   границе объективно есть: граничная зона давала 34.6 dB против 40.4 снаружи и 45.4
   внутри. Это была ошибка измерения, а не дефект кодировщика. Проверка: тот же клип,
   закодированный **без областей вообще**, даёт на той же зоне 27.2 dB против 38.4 и 40.6
   у соседей — провал на границе есть и там, где кодировщик обращается с кадром
   единообразно. Причина в самой метрике: зона `boundary` была шириной в один пиксель и
   ложилась ровно на силуэт объекта — самые сложные для кодирования пиксели кадра, — а
   зона `outside` была «весь остальной кадр». Сравнивались зоны с несопоставимым
   содержимым.

   Исправлено: пять концентрических полос равной толщины (±2 блока вокруг края) и
   **дифференциал** — те же зоны на адаптивном кодировании минус те же зоны на базовом.
   В такой форме ответ обратный: граница выигрывает **больше всех**, +8.7 dB против +2.3
   на внешней полосе. Осталась малая аномалия, стабильная по сценам: полоса сразу внутри
   края выигрывает на **1.0–1.5 dB меньше**, чем полосы по обе стороны от неё
   (`boundary_dip`). Порог в `check.sh` — 3 dB, так что это ловится как регрессия, если
   вырастет.

   Урок общий: абсолютный PSNR по зоне не значит ничего без базового кодирования той же
   сцены. Любая новая зонная метрика должна быть дифференциальной с самого начала.
5. **VMAF: ROI и background, парой** — единственный незакрытый пункт этапа. Линковать
   `libvmaf` прямо в `roi_metrics` (см. замечание в блоке E).

Проверяемо целиком на синтетике, без внешних датасетов и без нового железа.

## Что из этого нужно продукту прямо сейчас

Если смотреть только на ta_vms, а не на ТЗ, порядок другой и короче:

1. Этап 2 целиком — приоритеты по типам объектов, ради которых всё затевалось.
2. Из этапа 1 — ROI-VMAF, чтобы приоритеты можно было измерить, а не обсуждать.
3. Этап 4 — если решим делать живое перекодирование.

Rockchip, SEI, NVENC и внешние датасеты продукту не нужны вовсе. Это стоит держать в
голове при планировании: расхождение между «сдать ТЗ» и «улучшить продукт» здесь
велико, и оно не разрешится само.
